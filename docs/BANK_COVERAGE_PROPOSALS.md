# Whole-charge funding

The daily 5:30 p.m. America/New_York profile check imports individual checking debits and creates one unapproved draft per uncovered charge. Each charge uses the first configured, enabled source able to cover its **entire** amount after reserves and existing draft allocations. An insufficient source is skipped; charges are never split and the checking balance deficit is not added to charge amounts. A negative posted balance and an overlapping pending total are not separate charges.

`bank_funding_charges` stores canonical checking identity, provider transaction aliases, amount, date, description and draft linkage. The explicit `pending_transaction_id` joins pending and posted versions; matching amounts alone never establish identity. A completed funding draft leaves a permanent charge link, preventing repeat funding. Cancellation suppresses recreation. Removed charges block approval/preparation. Amount changes revoke an unprepared draft's approval and require a new review. Provider categories such as LOAN_PAYMENTS and TRANSFER_OUT do not exclude a checking debit: they include the user’s $286.86 and $350 charges. Only an outgoing debit containing an actual tenant-owned transfer memo is excluded as already tracked.

`bank_funding_feeds` chooses a single transaction reader for each canonical checking account, avoiding duplicate imports through shared logins. Review refreshes that reader when needed. The first import retains posted history for explicit manual selection, rather than automatically funding historical expenses. Pending entries and new posted debits after initialization are eligible. Missing transaction identities or currency evidence are never synthesized from a pending sum. A manual charge and a later same-amount bank entry within seven days are held as a possible duplicate, not automatically funded twice.

Manual entry selects a banking profile's permitted credit-line-to-checking route and either a known bank charge or a missing charge with a reference, date and full amount. References and potential duplicate amounts/dates are checked under the tenant lock. Both scheduled and manual drafts require explicit review before bank preparation. Source capacity is rechecked on review, approval and preparation. The user alone submits the bank transfer.

An older aggregate coverage draft has no charge attribution, so new automatic charge funding for that checking account waits for it to be resolved. No historical scheduler run is replayed on deployment. The queue polls stored drafts without a Plaid call. Schema changes add two tables through the existing application startup table creation; deploy Web successfully before the worker.

Validation includes the $286.86 and $350 example, skipping a $11.64 HELOC, repeated runs, source reservations, shared logins, pending-to-posted identity, amount changes, removed debits, manual duplicates, cancellation and mandatory review. No real bank transfer is used for QA.

Coverage memos use `Cvr <charge name> <MM-DD> <short draft reference>` within the bank assistant’s 34-character ASCII limit. Long names are shortened; the full charge description remains in ELIS. Legacy memos are upgraded during unapproved draft review, immediately before a ready draft starts preparation, or after an explicit `preparation_not_started` outcome. In-flight, failed, posted, and completed memos remain unchanged so original bank entries can still be matched.

The full-charge queue uses one explicit approval screen in the bank assistant. Review draft validates current charge identity, full amount, route and source capacity through `/prepare-charge`, then reserves `preparation_requested` before sending `ELIS_PREPARE`. This claim is not bank preparation or submission: the extension still requires the user to approve before opening/filling the bank form. Changed amounts stop and refresh the queue. Legacy aggregate/custom-amount flows retain their existing ELIS review. Inline row progress covers both charge draft creation and bank checks; no intermediate ELIS confirmation modal is opened for whole-charge drafts.

## Posted charges absorbed by checking

A posted expense no longer needs a new credit draw when a subsequent bank balance confirms both posted and available checking cash are at or above its protected reserve. Profile sync matches the canonical reader's posted transaction ID, amount, date and USD currency, then performs a fresh balance read after the transaction feed. Only eligible Plaid charges are reconciled; pending charges, manual entries, and approved/prepared/in-flight transfers are preserved. An unapproved draft for a reconciled expense is cancelled, not marked as a completed transfer.

`bank_funding_reconciliations` retains the posted identity, amount, checking balances, reserve, observation time, and any retired draft ID/status. `reconciled` means the funding need was absorbed by the posted checking ledger, not that a particular incoming transfer was matched or a reversed debit paid its merchant. Changed amounts or a return to pending invalidate that settlement; the audit survives. A second balance read is needed only when unresolved posted candidates exist. The additive audit table is created by Web startup before deploying the worker.

Regression coverage includes restored checking with stale posted expenses and an unapproved $29 fee draft, followed by the 5:30 check preparing exactly $29.99, $1,000 and $989.06 from the sufficient credit line, skipping the insufficient HELOC. Repeated checks neither recreate retired drafts nor duplicate the three new drafts. Missing/foreign-currency/insufficient balances, mismatched provider identities, other feed readers and in-flight transfers cannot be reconciled by this rule.
